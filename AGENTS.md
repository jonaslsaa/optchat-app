# OptChat app

This codebase is yours: what it's for and how it's built are your call, and you'll keep building on it.

The app for pi-optchat. `docs/design.md` has the design, its decisions and the build order, `docs/server.md` the server and its protocol, `docs/ui.md` the UI.

- **`README.md` is the product page:** what the app does, in plain words, for someone who has never seen it. No internals, build notes or status there. When you land something, a feature a user would notice gets a line in the README; how it is built goes in `docs/`, and decisions, the build order and what is being built in `docs/design.md`.
- **What the product is:** one chat per profile, never a list of threads: the sidebar holds a profile's main chat and its connected windows. The memory is the product, so it is visible: every summary opens into its originals, and the memory view is what the agent reads this turn. Agents and connected windows are first-class: live, and yours to read, steer, interrupt and resume. Never block the user: summarizing and handoffs show as a quiet gauge, never a spinner in the way. Small and keyboard-first; cost and cache numbers stay honest and visible; what the terminal already has becomes a panel before anything new is invented.

- **Layout:** `src/protocol.ts` is the one schema between server and UI (typebox; types are inferred from it, and it imports nothing from Node). `src/client.ts` is the typed client. `src/server/` is the Node server. `src/desktop/` is the Electron shell around the two (`docs/desktop.md`): it starts the server and opens a window on the page, and nothing else. `src/ui/` is the page (React, Vite, Tailwind), which the server serves once built; it has its own `tsconfig.json`, and its logic lives in `transcript.ts` (no DOM, tested) and `store.ts`, not in components.
- **A client, never a second brain.** Profiles are read through `pi-optchat/files`, which is all the app knows of pi-optchat's files; agents run in `pi --mode rpc`. The app writes a profile only with pi-optchat's own functions from there, under its rules: a new profile (`createProfile`), its settings (`updateConfig`) and its instructions (`saveInstructions`). Its memory is Pi's alone to write.
- **Plain TypeScript on Node**, run without a build step (`node file.ts`), so only erasable syntax: no enums, no parameter properties. No `any`. npm, `node --test`, the fewest dependencies that do the job.
- **When unsure how to solve something, look at T3 Code first** (`~/Downloads/t3code`, MIT, read-only) and take its solution where it fits: components and solutions (the composer, markdown and code rendering, diffs, tool-call blocks, the Pi RPC client), not its thread-per-task architecture, server, multi-provider layer, source control, cloud, mobile, Effect or monorepo. Code copied from it gets an entry in `THIRD_PARTY_NOTICES.md`.
- **Safety:** tests and every manual run use a throwaway `OPTCHAT_HOME` under `/tmp` (`test/support.ts`), and a throwaway folder for the app's own files (`OPTCHAT_APP_HOME`, or `startServer`'s `app`). Never open, lock or write the real `~/.optchat`, never install into or change the user's own Pi (an install is tried only with `PI_CODING_AGENT_DIR` and the app's folder under `/tmp`), and kill only processes you started. A server is told where its Pis run (`cwd`, which has no default), and the fake Pi refuses to run in a home folder and writes only where it is told (`FAKE_PI_STOPPED`): nothing a test starts runs or writes in yours.
- `npm run check`, `npm test`, `npm run test:live` for real turns through Pi (`PI_OPTCHAT=<checkout>` to run a pi-optchat checkout), and `npm run test:ui` for what only a browser decides: whose a key is and where the focus goes (`test/ui.ts`, the built page in your installed Chrome against the fake Pi). A part of the page with keys of its own, where Esc must not stop the chat's run, is marked `data-keys` (`src/ui/keys.ts`); a new one gets a case there.
- **Look at what you changed in the UI:** `npm run screenshots [directory]` saves a PNG of every main state to `/tmp/optchat-app-shots` (empty profile, long history, streaming reply, queued message, connected and completed windows, two profile tabs, narrow, dark, a Pi that stopped, settings, a chat running outside the app, the first run, the agents panel, the memory view and a search of it, the GitHub list, the desktop window's top row, a profile's settings, talking to an agent, the model picker, a message pi-optchat did not take, a message sent while Pi starts, the list of commands, a selection with its Quote button, the usage page, a reply with formulas and a table, images with a message, a reply that names files, the New Profile dialog, the update button, a profile's instructions with the editor they open in and its list; `--dark` for all of them in dark mode). It runs the real server and page against throwaway profiles with the fake Pi in your installed Chrome, with fixed clocks, so two runs of the same code give the same bytes. Read the PNGs before and after a UI change; add a state to `scripts/screenshots.ts` when you add one to the UI.
