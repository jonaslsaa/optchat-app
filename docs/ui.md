# The UI

A web page the local server serves: React, Vite and Tailwind, the same stack as T3 Code, with its looks (see `THIRD_PARTY_NOTICES.md`). It needs no Electron; the desktop app is a window around the same page ([desktop.md](desktop.md)).

## Run it

```bash
npm start                 # builds the page, then serves it at the address it prints (http://127.0.0.1:4780/#<token>)
npm run dev               # the server, and Vite with hot reload (open the address it prints: Vite's, with the token)
npm run screenshots       # a PNG of every main state, in /tmp/optchat-app-shots
```

## What you see

- **Profile tabs** on top, only once two profiles are open, with a + that opens another. A tab has a dot while a window of its profile is working, and a red one when a window's Pi failed. With one profile there is no tab bar: its name sits in the title bar and opens the list of profiles. Under that list is **New profile…**, as in the desktop app's File menu: a small dialog asks for a name, pi-optchat makes the profile as it makes the first one ([setup.md](setup.md)), and it is opened in a tab beside the others, behind the dialog's second step. A name that will not do, or one there is already, is refused under the name in pi-optchat's words; Esc, Cancel or a press beside the dialog makes nothing, and the chats that are running go on. The second step, **Bring your history?**, has a card for each source the [Import](#import) page reads, with what this Mac has of it (none picked), and two ways on: **Start empty**, which Esc is too and which leaves the keys in the new chat, and **Choose what to import…** (the keys are there), which opens the Import page on the sources picked. A new profile has no messages, so it is never asked how its history joins them. When none of the sources has anything on this Mac, the step says so in place of the cards, and its way on is **Bring a ChatGPT export…**, the same page with only its drop zone to use. While the setup lacks something (pi-optchat missing or too old) there is no second step: nothing could be imported, and the dialog closes on the new chat. The first profile, named on the first page, is asked the same in that step alone. A profile has a small badge in front of its name, in the tab and in the title bar: two letters in a colour, both derived from the name as T3 Code derives a project's (`badge.ts`), so the same profile looks the same everywhere and nothing is kept or chosen. The colours are T3 Code's without its red, which here is a failed window's, and on a light page each is dark enough for its letters to read on their tint (4.5:1 or better), so the warm ones are browner than their names.
- **Windows** on the left: the main chat, then connected windows, and at the foot two shelves, as T3 Code's "Working" and "Settled" are: **Handing off**, open, and under it **Completed**, closed, each with how many it holds, a click on its header opening or closing it, and shown only when it holds one. A window is where its state puts it (`completing` and `completed`, [server.md](server.md); `shelved` in `store.ts`), so one completed that starts a new conversation goes back up. A closed shelf still shows the window you are in, and which shelves are open is kept in the page for every profile. An open window's row has Complete (✓), and one whose Pi stopped or failed has close (✕), which removes it. A row on a shelf has no button: what is handed off stays, the row of a handoff under way turns, and the chat's top row has "Handing off…" in place of Complete. Complete, from either or typed as `/complete`, shows the main chat at once if the window was the one shown, so you see the handoff arrive; asked again while it runs, it is no error. The desktop app's right-click Remove takes any connected row away, as ✕ does: a completed one, a handoff whose Pi never answers, or an open one, whose conversation the main chat then gets from its transcript. In a plain browser, which has no such menu, a row on a shelf stays until the app's server stops. The button above them opens a connected window, which sends the main agent nothing until its first message and is "Untitled window" until then. Hold ⌥ to see the digit of each row in sight, top to bottom. A double-click on a connected window's name, in its row or in the chat's top row (or F2 on its row, or Rename in the desktop app's right-click menu on the row), turns it into a box to rename it in: Enter or a click away keeps what was typed, Esc what it was called, and an empty name gives back the one it had from its first message. The keys in the box are its own, so Esc there stops no run, and over a narrow chat closes the windows only when pressed again. On a narrow page, where a click on a row closes the windows, the top row is where a double-click renames. The name is the server's, for every page, as long as the window lasts (`rename`, [server.md](server.md)); the main chat keeps its name. On a narrow page the windows lie over the chat, opened for one pick: a window picked, a new one, Esc and a click beside them close them, and a page made narrow starts with them closed.
- **The chat** in the centre. The main chat is the profile's log, read from disk a page at a time as you scroll back, so it shows with no Pi running. A connected window shows its own conversation, which only its Pi has until Complete hands it over. A completed one stays as it was until your next message, which begins a new conversation in the same window: the view starts empty, and the finished one is in the main chat.
- **The chat's rows.** A tool call reads as what it did ("Ran `npm test`", "Read src/client.ts, lines 40–99", "Looked back at 128+2", "Started an agent: …") and opens to what it printed. A picture a tool returned (a screenshot the agent read) is drawn over what it printed, 16rem high at most as T3 Code has it, and a click shows it large as your images are: from what Pi sent while the run lasts, and from the profile's file once it is logged. One the profile no longer has says "Image unavailable" in its place, and an agent's chat has none, since it does not carry its images (`chat` in `agents.ts`). Opened, the line is there whole and can be selected, and above what the call printed is only what the line does not say: the text told to an agent, a command of several lines. An edit or a write that was done is the diff it made, the lines it kept plain and those it took out and put in in red and green, with how many of each beside the file's name ("Edited src/pi.ts +23 −4"); it scrolls in the box it opens in, and what Pi printed under it is left out, since the line says it. It is made from what the agent asked for, which is all the log keeps, so it looks the same after a restart: without the file's line numbers or the lines around the change (Pi's own diff has those, and pi-optchat does not log it). While the call runs, and when it failed, it is the text it was given. Arguments show as JSON only where the app has no words for them: a tool it does not know, or an argument its line leaves out (a search's `glob`). While the agent works, a line under its reply says for how long, and while it thinks, the last line of its thought in plain words (without Markdown markers, `thoughtLine` in `transcript.ts`); once it has thought anything, a click opens all it has thought in this reply so far, drawn as Markdown as it comes, in a box that scrolls. It stays open for the rest of the run (and the next), and is gone when the run ends: pi-optchat does not log thought, so a finished reply has none to show. Only a model that sends its thought has any: Claude sends a summary of it, OpenAI's models a summary when they make one, and many send nothing. Finished work folds to one line, which says so when a call failed. A subagent's report goes by the title it was started under. A file a reply names, in inline code or as a link (`src/ui/App.tsx:42`), opens in your editor at that line, when it is a file in the folder the window runs in; one that is not stays as it was written ([server.md](server.md#files-the-chat-names)). A reply can be copied whole, and so can a report and a message of yours (the button shows when the pointer is on the row); a table in a reply copies as it was written or as CSV, and a formula (`$…$`, `$$…$$`) is typeset. A price or a shell variable is not a formula: by Pandoc's rule, a little stricter, a `$` that opens one has no space after it, and the one that closes it no space before it and no letter, digit, `\` or `{` after, so "$5 and $10" and `$HOME/$USER` stay as written. What the agent had written when you stopped it stays in view. Select part of a reply, of a report or of a message and a "Cite" button stands at the end of the selection: it puts what is selected over the box you type in, as a chip, so one finding of six can be answered. See [Citing](#citing). The button stands under the last selected line of the reply or report the selection began in, wherever the selection runs on to, and Esc on it takes it and the selection away without stopping a run. When you complete a connected window, the handoff its agent writes for the main chat is a folded line under the conversation ("Handed to the main chat"), not a reply to you.
- **The panel** on the right, behind one button in the main chat's title bar, which has a dot while an agent works. It lists, one under the other, the main chat's agents and what it named on GitHub, each under a small heading and only when it has something to list (with neither, one line says what will be there). A list shows its first rows and a "Show more". It is the main chat's, so a connected window has none, and on a narrow page it lies over the chat as a sheet: the focus stays in it, Esc closes it (from an agent's chat it first goes back to the lists), and the focus then returns to what opened it. Its keys are its own ([Whose a key is](#whose-a-key-is)).
- **Agents** in the panel, under "Agents · 2 running" while some work. The list has the agents at work first, then the newest, each agent's own agents under it: its title (or the first line of its task), how long it has worked, and what it is doing now in the words of the chat's tool rows, or how it ended. A click opens the agent's chat in the panel, in place of its lists and with the way back at its top: its task, its work and its answer, drawn as the main chat is. The name on a report in the main chat opens the agent it came from, and so does an agent's line under the call that started it. While the main chat's agents work and the panel is closed, a line over the composer says how many and which, and opens the list. Under an agent's chat you tell it, interrupt it and stop it, and a message to one that has ended starts it again ([Agents](#agents)). See [Agents](#agents).
- **GitHub** under the agents: the issues and pull requests the chat named by link. Each is a link to GitHub with its title, its repository and number, how it stands (open, draft, merged, closed) and, for an open pull request, its checks and its review. The latest named comes first, open or not: what the chat is on now is at the top. See [GitHub](#github).
- **The memory view**, in the main chat's place, behind Chat / Memory in its title bar (⌥M): the lines the agent reads its memory as, oldest first and opened at the newest, under the day each begins on. It says how many messages there are and since when, how many lines the agent reads them as, and how much of its budget those take. A line is a summary of 2, 4, 8 or more messages, shown as it is stored, or one message; it opens into the two lines it was made from, and a line of one message into the message as the chat draws it. What you opened stays open while the view is read again ("Not summarized yet" is a line whose summary its Pi has still to write). ↑ and ↓ walk the lines, → opens one and ← closes it. Its search box (⇧⌘F from anywhere in the chat, and ⌘F here) finds the messages that say what you type, newest first, and a message that was found opens in the tree, where it is. A message sent from here is answered in the chat. It only reads ([Memory view](#memory-view)).
- **Find in the chat** (⌘F), as a small bar over the chat's top right corner, in the main chat and in a connected window: what you type is marked wherever the chat shows it, the match you are at marked stronger and brought into sight, with which it is and how many there are beside the box ("3/12"). Enter goes to the next one and ⇧Enter to the one before, round the ends; Esc closes the bar and the keys are back where they were (a key an input method takes, to pick what it offers, is neither). It is plain text in any case (Æ is æ), and what it finds follows the chat as it grows, so a reply is found while it is written. See [Find](#find).
- **An empty window** says what it is in the middle of the page, with the composer under it.
- **Import**, from the list of profiles ("Import history…", into the profile in front), the File menu of the desktop app (Import History…), the memory view's header and an empty main chat: other tools' histories brought into the profile's memory, on a page in the chat's place. While an import runs or waits, the chat has a line in place of its composer. See [Import](#import).
- **Usage**, behind the chart in the title bar: what the profile in front cost, in the chat's place as the settings are. See [Usage](#usage).
- **Settings**, behind the gear in the title bar, in four tabs: *General* has where new windows run, in the desktop app whether the Mac is kept awake while agents work ([desktop.md](desktop.md)), and what a chat needs (a newer Pi that is out in grey beside it) with whether it is there ([setup.md](setup.md)); *Appearance* has light or dark, the theme and the sidebar's art ([Themes](#themes)); *Profile* and *Instructions* have the settings and the instructions of the profile in front ([below](#a-profiles-settings)). The arrows go from tab to tab; the page opens on the tab last chosen while the app runs, and on General while a chat still needs something. With no profile there are only General and Appearance. Before there is a profile, that setup is the page. A main chat that a Pi in a terminal has open says so where its composer would be.
- **The composer.** You can always type. While the agent runs, Enter steers it, ⌘Enter queues the message for after the run, Esc stops the run and puts what was still queued back in the composer, and ⌥↑ puts it back while the run goes on (Pi's `clear_queue`, as Alt+Up in its terminal; the first waiting message says so), while the keys are in the chat ([Whose a key is](#whose-a-key-is)). ↑ in an empty composer brings back the last thing you said in the chat, as a shell does, ↑ again the one before, and ↓ goes forward; the keys do that only while the box is empty or holds one of those messages as it was sent, and from its first line (↑) or its last (↓), so they never take what you are typing and still move through a message of several lines (`recalled` in `transcript.ts`; a message said twice is there once). What you were typing stays with its window, and is there when the page is opened again (the browser keeps it, with the open profiles), until you send it or its window is gone (a connected window is, once the app has been started again). The line under it speaks only when there is news: how to steer a run, that Pi is starting, agents at work, summaries still to write. When a window's Pi has stopped, a box above the composer says why and what to do.
- **A message you send is in the chat at once**, with the agent at work under it ("Starting Pi" while the window's Pi starts, which a window's first message waits for), and not only once Pi has it. Pi's own copy of it then takes its place, in the same row. If it was not sent after all (the server or pi-optchat refused it, or it failed), it leaves the chat and is back in the composer with its images. It is kept nowhere (`Live.sent` in `transcript.ts`). A command (`/…`) is no message and is not shown, but a skill (`/skill:<name> …`) is one; a message sent in a run waits under the chat as before, and is not shown twice.
- **What Pi says in passing.** Pi and its extensions say things outside the chat (`notify`): why pi-optchat did not take a message, a warning, a thing it did. Each stands in a box above the composer of the window it was said in, in the colour of its kind, until you dismiss it (its button, or Esc in the chat while no run is on) or send your next message. They are no part of the chat and are not kept: a page that connects again shows the ones of the latest run. A message an extension answered itself (`handled`) that is not a command was not taken, so it goes back in the composer, as one the server refused does.
- **Commands.** A `/` at the start of a message opens a list over the composer of what the window's Pi runs for a message that begins so: your prompt templates, your skills (`/skill:<name>`) and the commands of its extensions, each with what it is for. Typing the name leaves the ones that have it, ↑ and ↓ move through them (while the list is open they are its own, and bring back nothing you said), Tab or Enter puts the command in the message with a space for what follows, and Enter sends a command that is typed out in full. Esc closes the list and nothing else. The list is Pi's own (`commands` in [server.md](server.md)), asked for when it opens, which starts the window's Pi as a first message would; that writes nothing in the profile's memory. A main chat's Pi that starts goes on with what waited for it, as after any start: summaries still to write, and a window's handoff, so a `/` can begin a turn of the main chat when a handoff is waiting. Until the list has come, Enter waits and sends nothing. Of pi-optchat's commands it has the ones that do something here: `/optchat instructions` and `/optchat import` in the main chat (the other words of `/optchat` open a screen of the terminal), `/complete` and `/tell-main` in a connected window. What a command answers is said above the composer, or asked in a question over it. A message that runs a skill, which Pi sends as the skill's file with what was typed under it, shows the skill as a chip by its name over what was typed (`skilled` in `cite.ts`, which reads Pi's form and the typed one alike, so the row sent at once already has it); the name opens the file. It is copied, brought back with ↑ and names a window as it was typed.
- **Files.** An `@` at the start of a message or after a space opens the same list over the composer with the files and folders of the folder the window runs in that match what is typed after it, the best first (`mentions` in [server.md](server.md)): its name, then its path, from the whole name to letters in order. A file taken is put in the message as Pi's terminal puts it, `@path` and a space, quoted (`@"my file.txt"`) when it has a space in it; a folder is `@folder/`, and the list then has what is in it. It is plain text: Pi reads the `@path` in the message as it would one typed in its terminal. Its keys are those of the list of commands, and while the next answer is on its way Tab and Enter wait. Typed up to a `/`, what is listed is that folder's, which is how a file deep in a folder outside a git repository is found. Only paths from the window's folder: no `~/`, no absolute path, no `..` (a link in it to a folder elsewhere is followed, as in Pi). Taken with the caret inside a path, the whole path is replaced. While the next answer is on its way a click on a row waits too.
- **Images** go with a message: paste one (⌘V with an image or a copied file on the clipboard; copied cells, which are text with a picture of them, are pasted as text), drop a file on the composer, or choose files with the button beside the model. Each waits as a small picture above the text with an × that takes it off, and a message can be images alone. PNG, JPEG, GIF and WebP of up to 10 MB each and 50 MB together are taken; another file is refused in words above the text, and the rest still go. Nothing is sent while a file is still being read. Pi makes an image smaller that is more than a model takes, and writes under your message where it did, for the model: the chat leaves that note out of your message (`yours` in `cite.ts`), so it is not shown, copied or brought back with ↑; a note that a picture could not be sent stays. The memory has it as Pi sent it. They stay with their window while you look at another, but not when the page is opened again: what the browser keeps is the text. In the chat a message shows its images, at once from what was sent and from the profile once the message is in its log. A click on one, or on an image a reply draws (only the profile's own: [below](#how-it-is-built)), shows it large over the page and everything on it (a modal dialog, so the focus is in it), and Esc, the × or a click beside it puts it away and gives the focus back. See [Pictures shown large](#pictures-shown-large). Every window the app runs takes them: the main chat, a connected window, and a connected window of a profile that a Pi outside the app holds. A message that waits in a run is listed by its text, or as "Image" when it has none, and Stop gives back the text of what still waited, not its images.
- **The model**, in the composer beside the button that sends: the mark of its provider, its name and how hard it thinks. A click opens the list it is picked from, and under the list a switch says whose model it is: the chat's own, or its subagents'. See [Model](#model).

### Whose a key is

One rule, in `keys.ts`. A part of the page that has keys of its own says so: the memory view while it stands in the chat's place (the top row over it is then its own too: the button that shows it has the focus until the view takes it), and the panel beside the chat. A key pressed belongs to the nearest such part around the focus, and to the chat everywhere else: in its composer, on its transcript and its top row, and on the windows at the left, the profiles' tabs and the notices too. A shortcut that is one part's runs only there. Shortcuts that are the whole page's (⌘B, ⌥1, ⌘,) run from anywhere.

- **Esc stops a run from the chat, and not from the panel or the memory view.** With no run on, Esc in the chat takes what Pi said in passing off the page. In the memory view it does nothing but end a search (in the composer under it, it stops the run). In the panel it goes back from an agent's chat to the lists and otherwise does nothing (as a sheet, it then closes).
- **What is nearer takes the key first.** A menu that lies over the page (the profiles, the New Profile dialog, the models, the commands a `/` lists, the files an `@` lists, and on a narrow page the windows at the left) closes on Esc wherever the focus is, and gives the focus back to its button. The box under an agent's chat interrupts that agent, while there is something to interrupt. The chat's find bar closes on Esc while the keys are in it, and they are then where they were before it; with the keys in the composer, Esc is still the chat's. A question Pi asks over the composer takes Esc as its No or Cancel, as in Pi's terminal, and the run goes on. A key that one of them took is no one else's.
- **A focus that is lost stays where it was.** When what had the focus is gone from the page, the keys are still in the part they were last in (by focus or by a click), for as long as that part is there. So a row that goes away under the focus in the panel never hands Esc to the chat, and a notice that is dismissed in the chat leaves Esc working.
- **The focus is not left on the page itself** where the app can tell where it belongs: opening an agent puts it on the way back, and the way back on that agent's row; "Show more" keeps it, and once nothing is left to show hands it to the list's last row; a menu closed with Esc gives it to its button; Enter in a settings field leaves it in the field; a profile name that was refused has it again; and after Stop it is in the composer.

`npm run test:ui` checks all of this in a browser (`test/ui.ts`): the built page in your installed Chrome, headless, against the fake Pi.

### What comes in

What you open comes in over 150 ms instead of being there at once, and leaves at once. It is one class, `enter` (`index.css`): the thing starts at no opacity, with `enter-grow` at 98% of its size, with `enter-from-left`, `-right` or `-below` a few pixels that way. `@starting-style` is the browser's name for how a thing looks before it is first drawn, so there is no timer, no state and no library, and only opacity, scale and translate change, which move nothing else on the page. With "reduce motion" set in the system there is none of it; the tests and the screenshots run that way, so they do not wait for it, but for one test with motion on, which slows the page's animations (CDP) and reads a list and a sheet as they come in.

- **Fades and grows:** the lists over the page (profiles, models, commands), the Cite button, the image shown large.
- **Fades and slides:** the panel as a sheet and the windows over a narrow chat, each with the shade behind it; the "Scroll to end" pill.
- **Fades:** the panel beside the chat; Settings, Usage and the memory view; what opens under a line (a reply's work, a tool call's details, a handoff, a line of the memory); what Pi says, asks and fails with above the composer, and the app's own notices; the tick of a copy.
- **Not, on purpose:** a switch of profile tab or of window, and the chat coming back from Settings (that is the page you were on: it should be there); the sidebar beside the chat, which is there when the page opens; heights, so a fold opens at once and what is in it fades; messages and tool calls arriving, and text as it streams, which fades by the block already; anything leaving.
- **What comes in again:** `enter` is for the moment a thing is first drawn, which is also when the chat is: a notice, a question or a failure that stands above the composer when you come back to the chat (from Settings, from another tab) fades in once more, and so does the app's "Set up" notice, which Settings hides. Nothing else that was there does.

A thing with a transition of its own (a `Button`) is put in something that enters, since one element has one `transition`.

### Themes

The Appearance tab of the settings (`Appearance.tsx`). **Color scheme** is light, dark or the system's, each tile a small window in the colours it would have. **Theme** is a card for each theme with a round for its light and one for its dark: a click on the card uses it in both, a click on a round only in that one, so light can be Grove and dark Iris. A ring with a sun or a moon marks the round in use. *OptChat* is the app's own colours (`index.css`), and the others are Blossom, Grove, Ocean, Ember and Iris. **Sidebar art** turns off the night sky those five draw at the top of the sidebar, under its top row, in their colours (`Art.tsx`); what is on it is white. A theme with no art colours has a plain sidebar.

**A theme is a file**, and the built-in ones are files too (`src/ui/themes/*.json`), read as yours are, so one of them is where to start. Yours are the `.json` files in the `themes` folder beside the app's `settings.json` (`~/.optchat-app/themes`), which "Open themes folder" opens; each is a card, read again whenever the settings are opened. The file:

```json
{ "version": 1, "name": "Dusk", "appearance": "dark", "colors": { "background": "#101820", "primary": "oklch(0.7 0.15 250)" }, "variants": { "light": { "background": "#f8fafc" } } }
```

`colors` are for its `appearance`, and `variants` may give the other one. A colour is named as the page's own colour of that name (`ROLES` in `themes.ts`: `background`, `foreground`, `sidebar`, `primary`, `message-surface`, …), and what a theme leaves out is the app's own in that appearance; code keeps its GitHub colours. `art-top`, `-mid`, `-bottom`, `-highlight`, `-secondary`, `-tertiary` and `-line` colour the night sky: all seven, or none. What a file says ends up in the page's CSS, so only literal colours are taken (`#hex`, `rgb()`, `hsl()`, `oklch()`, `oklab()`, `lab()`, `lch()`), with nothing else in them: a file with anything else, a colour no theme sets, or no name of 48 characters at most is a card that says why, and is never drawn. The theme drawn in each appearance is kept in the settings by its file's name (`palette`); one that is gone, or that is no theme any more, leaves the app's own colours. The page keeps what it last painted in the browser too, so a reload paints it before the server has answered.

### Pictures shown large

T3 Code's image viewer (`Picture.tsx`): its looks, keys and zoom, without its downloads, videos and copy.

- **A message's pictures go together.** The pictures of one message, one reply (with what its tool calls show) or the images waiting in the composer are stepped through with ← and →, round the ends, or the buttons at the sides, and "2 / 5" under the picture says where you are. One picture alone has neither. What is one message is a mark on the page (`data-gallery`), and the pictures are read from under it when one is opened, so a picture drawn anywhere in a message is one of its own with nothing more to do.
- **Zoom.** A picture is fitted to the window, never made larger than it is, and zoomed up to eight times that. A click zooms in two times about where it was, and out again; a pinch, or the wheel with ⌘ or Ctrl, zooms about the pointer; + and − zoom by half again, and 0 fits it again. Zoomed, the wheel and a drag move it, and so do the arrows, before ← and → step once it cannot go further sideways. A drag is no click beside it: it closes nothing, and zooms nothing. Another picture starts fitted.

**One chat, three sources.** Every item in the chat is a log entry, or what a message Pi has not logged yet will be logged as (by pi-optchat's own `said`, from `pi-optchat/core`). So a reply looks the same while it streams, when it has ended and after a restart, and keeps what you opened in it. The live test checks that the two readings agree on a real turn.

**Joining the log with the run.** pi-optchat dates an entry with its message's time and logs a run in order, so a message of the run counts as logged once the log has an entry of its time, and so does everything before it. That is an interim rule: a run number published by pi-optchat would be sound where timestamps are not.

**Keys.** A row's key is its first entry's number in the log, and what a run has said and the log does not have yet is numbered on from the log's last entry, which is the number the log will give it. A connected window's conversation is numbered by its place in it.

**Reconnecting.** Windows live in the server. The page asks `windows`, then `records` for each, and replays them; a gap in the pushed record numbers makes it ask again, and read again what the run said. A lost connection is retried every second, from one place: the socket's closing.

**A reply is let out at a steady pace while it streams.** The network brings it in bursts: a real Claude reply comes some 10 letters every 33 ms, then nothing for a quarter of a second, then 120 letters at once. The page shows what has come a little each frame instead, faster the further it is behind, so all of it is out within about 0.2 s, and up to a word's end (`paced` in `transcript.ts`; `useShown` in `Markdown.tsx`). What its end has opened and not closed yet is held back until it is, so it never flashes as it was written: a `**`, `` ` `` or `$` on its last line, a `$$` formula, and a table's rows before the line under its head (`closed`), at most 80 letters of it. What was there when the reply was drawn, and all of it once it has ended or was stopped, shows at once: nothing waits for the pace but the letters still coming, and the copy button, the log and the memory have the reply as Pi wrote it. Each new block fades in, as in T3 Code. With reduced motion there is no pace and no fade. Claude Code's terminal does something of the kind: it shows a reply a whole line at a time.

**Code is coloured by Shiki, which the page does not load until a code block names a language.** Shiki, its light and dark theme and each language's grammar are chunks of their own, fetched on first use; the code shows plain until they are there, and stays plain in a language Shiki does not know. A token's colour is CSS `light-dark()`, so it follows the page's `dark` class with nothing drawn again. While a block streams, the lines it had are kept and only what came since is read, on from where the grammar stood at the end of the last whole line.

**Formulas are drawn by KaTeX, which the page does not load until a reply has one.** KaTeX, its styles and its fonts are a chunk of their own (`Typeset.tsx`); until it is there a formula shows as it was written, and so does one KaTeX cannot read, such as a formula still streaming, so no error ever flashes. `trust: false` keeps it from writing links.

**Nothing in a reply is fetched on its own.** The agent reads web pages and files that may tell it what to write, and a Markdown image is fetched the moment it is drawn, with whatever its address carries. So only two kinds of image are drawn: the profile's own (`/images/<profile>/<name>`), and a PNG, JPEG, GIF or WebP on this machine by its absolute path (`![chart](/tmp/chart.png)`, which the app's prompt tells the agent to write), which the page asks this server for (`/file`, [server.md](server.md)) and which, once it is no longer there, reads "No image at <path>". Any other image is shown as a link, and links open in a new tab that knows nothing of this one. The server backs this with `Content-Security-Policy: default-src 'self'`.

## Agents

pi-optchat tells an RPC host almost nothing of its agents: a count in the status line, the id the `spawn` call answers with, and the report. What an agent is and does is in the profile's files, which pi-optchat writes as it goes: a record of each run (`runs/<id>.optchat.json`, read with pi-optchat's own `readRuns`) and the run's Pi session file, which grows by a line as each message ends. So the server reads those ([server.md](server.md): `agents`, `agent`), and the panel shows an agent's messages as they end, not its words as they are written.

- **In the chat that started them.** Under a `spawn` call is a line for each agent it started, as the list has it: the same mark, its title, what it is doing now or how it ended, and how long it has worked, which a click opens in the panel. A reply that is folded shut shows them under its fold while one of them works; once all have ended they are folded away with the rest of its work, and their reports are in the chat by then. An agent the list does not have (its record is gone, or it ended before the newest eight the list keeps) has no line, and the call says what it started, as it always did. An agent's own agents are not there: they are the panel's, under the agent. In an agent's chat in the panel, its own calls have the lines of its agents the same way.
- **Over the composer**, while the main chat's own agents work and the panel is closed: a dot, "2 agents working", and each one's title and how long it has worked, on one line, cut short where it is full. It goes by the count in the status line, as the dot on the panel's button does, and names the agents the list has. A click opens the list. It is not there while the panel is open, which says it, and the line under the box no longer counts agents. Claude Code shows its agents the same two ways, under the call that started them and as a line by its prompt.
- **When it is read.** When the panel is opened, when the main chat changes (its Pi starts or stops, its status line changes, a message of its run ends, the log grows: an agent starting and a report arriving are among these), and every two seconds while an agent works: with the panel open by the list, and while a Pi in a terminal has the chat (it tells the app nothing of the agents it starts); with the panel closed by the count in the status line of the app's own Pi, which is also what the dot on the button goes by. Nothing is watched. The panel reads the list while it is open, and the chat while it is closed, so one reads it at a time. A read is pi-optchat's `readRuns`, which reads every record the profile has kept: some 30 µs a record of 7 kB (35 ms for 1,000, 90 ms for 3,000, on an M-series Mac), and what is sent is the same few dozen kB however many there are.
- **An agent whose Pi is gone.** A record can say `running` after the Pi that ran the agent died; pi-optchat corrects it when the profile is next opened. Until then the server asks whether any Pi has the profile open, the app's or one in a terminal, and where none does such an agent is `interrupted`.
- **Agents a restart cut off.** When a Pi closes or crashes while agents work, interactive Pi resumes them the next time it opens the profile; the app's Pi (`--mode rpc`) does not, since that spends tokens. So after a restart one bar with the yellow notices has a line for each profile whose own agents were cut off, open as a tab or not: "work · 2 agents were cut off when Pi closed", Resume and a dismiss. Resume opens the profile, starts its Pi if none has it, and has pi-optchat resume them as interactive Pi would (their own agents go on through them, and the main agent is told once). Cut off is what pi-optchat marked `cutOff`, or, in a profile no Pi has open, a record still saved as running or waiting (pi-optchat marks those when the profile is next opened); paused and stopping ones are not, and pi-optchat does not resume them. Dismissing a line keeps it away, in this browser, until an agent of that profile that started later is cut off; the agents are still in the list, and each can be started again from its chat. The bar is read when the page connects, after a Resume, and after a message started an agent again. A main reply that was cut off with no agents is not here: pi-optchat keeps no record of it to resume, and puts what you had sent and nobody answered back in the memory with a notice of its own.
- **A Pi on an older Pi or pi-optchat.** A Pi keeps the Pi and pi-optchat it started on. When the server finds a newer one installed and that Pi at work, it does not stop it (below the cut-off lines, "work · Its Pi started before pi-optchat 0.12.2 was installed", or "Pi 1.5.3" after a patch of Pi, and **Restart**, which does it and stops what it was doing). One that has nothing to do the server starts again by itself, so there is no line for it ([server.md](server.md#windows)).
- **Talking to one.** Under an agent's chat is a box: what you send reaches an agent at work after its current tool calls, and starts one that has ended again in the conversation it had. You do not choose between the two; the server does, by how the agent stands ([server.md](server.md#agents)). Until the agent has read a message it waits above the box, as in the main chat. **Interrupt** cuts what the agent is doing now, so it goes on at once with what you told it, or waits (`Paused`) for your next message; **Stop** ends it and the agents it started, and tells the agent that started it that you did. Each is there only while it would do something, and its line says how the agent stands: at work, done and failed in colour, the only colour in the panel.
- **What pi-optchat refuses** is said above the box in its own words, and your message is still in the box. It is said for as long as the agent stands as it did. One refusal is known beforehand: an agent's own agent that has ended is resumed only by the agent that started it, so it has no box, and a line that says which agent that is. While it works it is told, interrupted and stopped like any other.
- **Esc in the box** interrupts that agent, as it does in Pi's view of an agent. Anywhere else in the panel Esc is the way back to the lists; it is never the main chat's Esc ([Whose a key is](#whose-a-key-is)).
- **What it costs the main chat.** A message to an agent goes through the Pi that has the chat, so the app starts the main chat's Pi for it if none has. pi-optchat also notes what you told an agent in the profile's log ("Direct guidance to subagent [id]: …"), so the main agent knows; it shows in the main chat as a message of yours.
- **What is left out.** The first message of an agent's session is its task under a view of the profile's memory; the panel shows the task alone. Connected windows are runs to pi-optchat too, and are windows here. An agent's words as it writes them (the panel shows a message once it has ended), taking a waiting message back, and images in a message to an agent.

`src/ui/agents.ts` has the list's order and words and what an agent's state allows, with no DOM (`test/agents-ui.test.ts`); `src/server/agents.ts` the reading and the asking (`test/agents.test.ts`, against the fake Pi, which answers for its agents as pi-optchat does: `test/fake-owner.ts`). The live test starts a real agent and follows it from `running` to `completed`, and tells, interrupts, resumes and stops one, and an agent's own agent.

## GitHub

The issues and pull requests the main chat named by their link, in the panel beside it. What names one, and how GitHub is asked, is the server's ([server.md](server.md#github)); the page only shows.

- **It is a partial list, and says so.** Its heading: "GitHub · PRs and issues the chat named by link". One the chat only ever called "#12" is not there, because nothing says which repository that is in.
- **When it is read.** When the panel opens, when a turn of the main chat begins or ends, and once a minute while the panel shows its lists, which is what makes the server ask GitHub again about the open ones. The server answers with what it knows and asks GitHub behind that, so while it says it is asking the page looks again each second.
- **Without the status.** With no GitHub CLI, or one that is not signed in, the list is there as the log has it (repository and number, pull request or issue), under one line that says which and what to do, with "Check again".
- **A row is a link.** It opens GitHub in a new tab that knows nothing of this one. Its address is made by the server from the owner, repository and number it matched, not taken from the chat.
- **What is left out.** Tracking (telling the agent when a pull request's checks fail or it is merged), a view of the pull request itself, and any change to one.

## Citing

A message can cite what was said before: words selected in the chat, or in the memory view a line whole (the button on it, and on a message a search found) or the words selected in a line or in an opened message. Clicking **Cite** (or the button on a memory line) adds a chip over the box you type in and opens a comment popover right where you clicked (after T3 Code's):

- **Flow A (plain cite):** leave the comment empty and press Enter, or click straight into the composer to type.
- **Flow B (comment on this cite):** type a comment in the popover and press Enter to save it (Shift+Enter adds a line), or ⌘Enter (Ctrl+Enter) to save and send right away. Clicking outside commits any edited comment.
- **Cancel / edit:** Esc on a brand-new citation cancels and removes the fresh chip cleanly without stopping a running agent. Each chip in the composer has a pencil button to add or edit its comment later (Esc there discards unsaved edits and keeps the chip as it was), and × removes it, as Backspace does in an empty box. Chips and their comments are part of the draft, so they are there after a reload, and ↑ brings a message back with them.

Sent, the citations are the first lines of the message, each with an optional sibling `<comment>` on the next line when it has one, and what you typed is under them (`citing` in `cite.ts`, and `cited` reads it back; nothing else knows how it is written):

```
<cite zoom="11953">the words that were selected</cite>
<comment>your comment on that quote</comment>
<cite zoom="11904+4">how the line begins…</cite>

What you typed.
```

- **The place is the agent's own.** `zoom` holds what pi-optchat calls the place: a message by its number, a line as its view heads it (`id+n`). The agent reads the message as it is written and can open the place with its `zoom` tool. The attribute has the tool's name because that is what makes a model go and read it: with `memory="9"` Haiku said it could look, and with `zoom="9"` it did (`npm run test:live` has the case). pi-optchat is not changed.
- **A place only where the log has one.** A row of the chat is a message of the log, by its number (`data-cite`); an answer in several blocks is one for each. What is cited is of the one message the selection began in: where it runs on into the rows under it, it is cited as far as that message goes. A reply that is still in its run, and a connected window's conversation, are in no log yet: they are cited by their words alone (`<cite>…</cite>`), rather than under a number that is a guess.
- **What is cited is cut**, at 2,000 characters for a selection and 200 for a line cited whole, and ends in "…": the agent can zoom to the rest. Comments are capped at 2,000 characters in the editor. Only what would end a citation or comment early is written another way (`</cite>`, `</comment>`), so code is cited as it was written.
- **In the chat it is a card** in your message (T3 Code's): how it begins, on two lines at most, and "Memory · 11953", with your comment under the card when it has one. A click on the card opens the memory view at that place, with its line pointed out; ⌘F finds text in both the card and its comment. The message as it is written is never shown, nor in a message that waits in a queue or in a window's name. A message from before this, with `>` before each line, is as it was.
- **Copied, a message is as it was sent**, so pasted into the box it is its chips, comments and what was typed again.
- **Left as it is:** what a search of the memory found is the message as it is written, so a citation shows there as that. A message that begins with what it cites is not a command to Pi, so the list a `/` opens is not there while the message cites something.

## Import

What Claude Code, its memories, Codex, Pi and OMP kept on this Mac, and a ChatGPT export, brought into the memory of the profile in front (`imports.ts`, `Import.tsx`). pi-optchat does all of it ([server.md](server.md#imports)): the page picks, and shows how it goes.

- **Sources** on the left, each with how many conversations it has and in how many projects, found by a scan of the files those tools keep: no model, no Pi, nothing written. A source is looked for once while the server runs; the button over them looks again. A source with nothing on this Mac is greyed. A ChatGPT export is not on the Mac where the page can find it, so it is given: dropped on the box under the sources, or chosen with its button. It goes to the server a piece at a time (with how far it is), and is then a source like the others.
- **Projects** of the sources that are ticked, busiest first (one with the same folder in two sources is two rows, each with its source's mark), each with its count, when its newest conversation began and its size. A project's box picks all of it, and says when only some is picked; its chevron opens it to its conversations, newest first, each with a box of its own. The range (30 days, 3 months, a year, all) leaves out what began before it, in the list and in what is imported; the filter only hides, by a project's name or a conversation's title, and what it hides stays picked. "Pick all shown" picks what the list shows. A row is drawn only once it comes near the screen (`content-visibility`), so thousands scroll and filter as ten do.
- **Nothing is picked** until you pick it: a large import keeps the profile's compactor busy for a long time, and that is what it costs.
- **The footer** is always there and says what the pick brings, by pi-optchat's own count of it (`importPreview`, asked a quarter of a second after the pick last changed, while "Counting…" stands there): how many conversations, how many messages are new and how many the memory has already, and about how many tokens the compactor reads for it (three times the text, pi-optchat's rule of thumb) and which model that is. What pi-optchat cannot read of the pick is "1 warning", which opens to the list. A profile that has messages is asked how the history joins them, over the footer, each way in one line with what it costs by pi-optchat's estimate for it: **Append** (the default) keeps the summaries it has and summarizes only what is new; **Rebuild from scratch** puts everything in order by when each conversation began and summarizes the whole memory again. A new profile is never asked. **Start import** starts it in the profile's Pi, which is started for it if none runs; why it will not (the chat is in a run, agents are at work) is said in pi-optchat's words.
- **While it runs** the page is a card with how far it is (messages and summaries, and a bar), what pi-optchat is retrying and why, and **Pause**. The profile's chat has a line in place of its composer, "Importing 4,210 / 12,960", with **Show**, which opens this page: pi-optchat takes no message in a profile that imports. Other profiles go on. Paused, or after a failure, the card has **Resume** (Try again) and **Discard**, which asks once more; so has an import that was running when the app quit, which pi-optchat then calls paused. The memory the profile had stays as it was until the import has finished, and a discarded import leaves it so.
- **Done**, the card says how many messages came in, has **Open memory**, and offers a first question to ask, which a click puts in the chat's composer. The chat and the memory view read the profile again: an import moves it to another memory.
- **Esc** closes the page, as it closes the settings, and an import goes on.
- **What is left out.** Picking single messages, an import into a connected window, importing on another machine than the one the app runs on, and a progress bar of the scan itself.

## Memory view

pi-optchat keeps a profile's memory as a log of messages and a tree of summaries over it: one for every two messages, one for every two of those, and so on. What the agent reads each turn is a row of lines that covers the whole log, the newest messages one by one and older ones as ever larger summaries. The memory view is that row, and the tree under it.

- **Where it comes from.** The server reads the profile's files with `pi-optchat/files` (`view`, `zoom`, `original`, `search` in [server.md](server.md)); the page holds the view, and what was read under the lines you opened. The app summarizes nothing and writes nothing: a summary the owning Pi has not written yet is "Not summarized yet".
- **It can trail the chat.** A Pi writes a message when it ends and a summary a while after, and saves how the view is folded only when that changes. So the view here is the last one saved with the messages since added to it, which is how pi-optchat itself reads it back, and can be a fold behind the Pi that is running.
- **When it is read.** When it is shown, when the main chat changes (its Pi starts or stops, the log grows), and every three seconds while that says too little: while the chat's Pi runs (it logs as it goes, and the page reads the log when the run ends), while a Pi outside the app has the chat, and while a line waits for its summary. The server keeps what it read until the files change, so such a look costs it a glance at them, and the page is drawn again only when the view changed.
- **A line is the same line for as long as the memory is the same one.** `128+64` is the 64 messages from message 128 on, as pi-optchat writes it. So what was read under a line is kept and lines stay open across a read; only a tool call that was read before it had printed is asked for again. An import moves a profile to another memory: when the view names another one (or the log got shorter), everything read is dropped.
- **What it costs.** On a profile of 19,000 messages (27 MB of log, 16 MB of tree): the first read takes the server about 0.2 s, and it is kept until the files change; the view is 176 lines, about 100 kB; opening a line is about 1 kB; from the largest line (1,024 messages) down to one message is ten clicks. The page never holds the log.
- **Search.** The box finds the messages that contain what you type, as the agent's own `search` tool finds them (it is pi-optchat's `Memory.search`, through `search` in [server.md](server.md)): the messages as they were said, never their summaries, nor the agent's logged looks into its memory; plain text, in any case (Å finds å); newest first, 20 at a time, with "Show older ones" for the next 20. Each says who said it, when, and the two lines around where it first says it, with the match in bold. What was found stands in the tree's place, and the tree stays under it: ending the search (Esc, the ×, an empty box) shows it as it was, open where it was open and scrolled where it was. A search reads the whole log in memory: 15 to 20 ms on a log of 19,000 messages (22 MB), so each letter typed asks again and nothing is indexed.
- **A message that was found opens in the tree.** The lines from the view's down to the message are opened (a line begins at a multiple of its length, so the page knows them without asking), the message's line is marked and brought to the top, and "Back to the messages found" shows them again. The search reads the log as it is now: for a message newer than the view the page has, the view is read again first. The lines that were opened stay open when the search ends.
- **What is left out.** Searching summaries, whole words or patterns; a match further into a message than its first; what was found is not looked for again when the log grows; the shape of the tree as a chart, a connected window's own view (it has no memory of its own: it reads the profile's), and anything that changes a memory.

## Find

⌘F finds in the chat that is on the page, as a browser's own find does, and as T3 Code's does in a thread (`find.ts`, `Find.tsx`).

- **What is searched is the text the chat shows**: what you said, what the agent answered, the reports, and whatever is open, such as a reply's work, a tool call and what it printed, or what the agent thought. What is folded shut is not on the page and is not searched until you open it. A long message or report that is shown cut short is there whole, so it is searched whole, and it opens when the match you are at is in the part that is cut off. The words of buttons, the times beside the messages and the line that says for how long the agent has worked are the page's and are left out; a file's name that opens the file is a button too, and is searched as the text it is.
- **How it matches.** Plain text, in any case, with a line break or a tab as a space. A match may run through a word in bold or a piece of coloured code, but not from one paragraph, list item or table cell into the next.
- **Where it starts.** At the first match in sight or under it, and else at the last one above: at the end of the chat, where you usually are, that is the newest. Typing does not move the chat while the match is in sight, and a text that is nowhere leaves it where it was. A match at the end of a line of code that is longer than the page is wide is scrolled to sideways, in its block.
- **Nothing in the page changes.** The matches are the browser's highlights over ranges of the text (the CSS Custom Highlight API), so no row is drawn again for them. A row is read again only when something in it changed, right after the change and before the page is painted: the marks follow a reply while it is written without going out and coming back. In a browser without that API find still counts and scrolls, and marks nothing.
- **The chat is the newest messages** (a page of the log, and those above it that were loaded). Find does not load the rest, and going to a match at the top of the chat reads no page above it, as reading back to there yourself does: under the box, "Search memory for …" (⇧⌘F in the bar) searches all of the profile's memory for the same text ([Memory view](#memory-view)), also when the chat has no match.
- **What is left out.** Whole words and patterns, finding in what is folded shut, and find in an agent's chat in the panel.

## Model

The model a window's agent runs on and how hard it thinks, picked where you type (`src/ui/Model.tsx`). The look and the keys are T3 Code's model picker, without its favourites, its provider rail and its other 1,500 lines.

- **One button.** It says the model the window runs on, and before its Pi runs the one it will start on: the model you picked for it, the one the profile keeps for its main chat, or Pi's own default. A model that cannot think has no level beside it.
- **The only colour is the provider's mark**: Claude's for `anthropic`, OpenAI's for `openai` and `openai-codex`, as their makers draw them. Any other provider has one plain box. Names and levels are in the colours of the text.
- **The list** has every model Pi can use, each provider's under its name, and the levels the picked model can think at beside it (under it on a narrow page). It opens over the composer, or under it in a chat with nothing in it yet. Typing finds a model by its name, its id or its provider, the best match first.
- **Keys.** The button is the next stop after the message. In the list the typing goes on while ↑ and ↓ move through the models. Enter picks one, as a click does, and the focus goes to its levels (→ goes there without a pick), where ↑ and ↓ move, Enter picks and ← comes back to the typing. The list stays open after a pick, for the level. Esc closes it and nothing else, wherever the focus is, and the focus is on the button again: a run goes on.
- **What Pi refuses** is said under the list, in its words.
- **Whose model.** The switch under the list:
  - *Main chat*: picked at once, in the middle of a run too (the request under way keeps its model). It is the profile's from then on, in a terminal as well. With no Pi running yet the pick waits for the first message.
  - *This window*, in a connected window: that window's alone. It starts on Pi's default, not on the main chat's model.
  - *Subagents*: the model of the agents the profile's chats start, which is one of the profile's settings ([below](#a-profiles-settings)) and is saved with its level. What pi-optchat refuses is said under the list in its words.
- **A chat that runs in a terminal** has no composer in the app. The notice in its place says the model the profile keeps for it; it is picked there.
- **What is left out.** The compactor model (in the settings), favourites and recent models, a shortcut that opens the list, and telling which models a provider no longer offers before Pi refuses one.

## A profile's settings

Everything pi-optchat's own settings page has in a terminal (`/optchat settings`, `/optchat instructions`), for the profile in front, on the settings page. With two profiles open, the tabs above choose which.

- **A row for each setting pi-optchat has**, in its order and its words: the label, what it does, its default, and on the right a switch, or a number with its unit (a percent is typed as a percentage). Which settings there are comes from pi-optchat ([server.md](server.md#a-profiles-settings)); the page has no list of them.
- **The compactor model** is the first row: `provider/id` in a field that offers the models Pi lists, and how hard it thinks, among the levels the model has. It is typed, so a model Pi does not list can be named. A model that has not the level the one before it was at is saved at the nearest it has, as in the chat's picker, and the row says so. The chat's model and its agents' are chosen in the chat ([Model](#model)), not here.
- **A change is saved when you leave its field or press Enter** (which leaves the focus in the field), a switch when it is flipped. Under the row it then says "Saved" and when the change applies, in pi-optchat's words; a chat that is running takes it without a restart.
- **What pi-optchat refuses stays in the field**, with its reason under the row, as pi-optchat gave it. The app checks nothing but that a number is one.
- **Instructions** are the profile's AGENTS.md in a text field, saved whole with Save. Beside it, T3 Code's "Open in" split button opens the file in your editor: the main part in the one files open in, the chevron lists the editors found on this machine, and the one picked opens it and is the one from then on, for files a reply names too (`editors`, `openInstructions` in [server.md](server.md)). With none it is "Open", in the Mac's text editor. The file is then the one to trust: typing not saved yet is saved before it opens, and when the window has the focus again the field reads the file again; what it read replaces the field only while the field holds what was read before, so typing is never lost.
- **What is left out.** Which thinking levels a model takes (all seven are offered, and a running Pi refuses one the model does not take; with no Pi on the profile nothing checks it until the next summary), putting a setting back to its default with one click, and a change made in a terminal while the page is open, which shows when the page is opened again.

## Usage

What the profile in front cost, in a range you pick: a page in the chat's place, as T3 Code's usage page is one. Another profile's is behind the same button in that profile's tab. What is counted, and how, is pi-optchat's ([server.md](server.md#usage)); the page only shows.

- **The figures are the terminal's.** The cost, the tokens, a share and the cached percent are written as `/optchat usage` writes them, from pi-optchat's own sums, so the page and a terminal can be held beside each other. The page adds a line for each role (the sum of its models) and the bars.
- **What it shows.** The estimated cost, large. Under it the tokens: all of them, the input that was new, what was read from the cache (and how much of all input that is) and written to it, and the output. Then whose the cost was, as one bar in four colours: the main chat, its subagents, the compactor that writes the summaries, and imports. Then the cost over time, in the same colours, a bar's figures when it is pointed at. Then the table: each role and each of its models with what it cost, its share, its output and how much of its input was cached. A role with one model is one line, which names the model.
- **The limits** are first on the page, whatever the period: how much of the subscription's five hours and of its week is used, each as a bar with its percent and when it resets, and under the heading how old the count is ("As of 3 min ago"). It is the count that came with the latest answer to this profile, which pi-optchat saves ([server.md](server.md#usage)); the page asks no one for it. What cannot be missed is said in words above the bars: that a limit is passed and requests **run on extra usage** until it resets, or that a limit is reached. A request that was refused for a rate limit is said in their place, alone: nothing is counted with a refusal, so what was counted before it no longer holds. The fullest window is named with it as it was, unless that window had already reset by then. A window that has reset since the count has no figure, only "Reset 16:30, not counted since". With nothing saved the page says "No data yet", and that only an Anthropic subscription reports its limits: an API key, OpenAI and Codex never give a count, and pi-optchat before 0.11.15 in the Pi that runs the profile saves none.
- **The ranges** are Last hour, Today, Last 7 days and All time: Today when the page is first opened, and after that the one last picked for the profile. While another period's figures are still on the page, they are dimmed.
- **When it is read.** When the page is opened, when a range is picked, with the button at its top, and when the main chat changes while the page is open: its Pi starts or stops, a message of its run ends, its status line changes (which counts its agents and the summaries still to write). Those are the moments the ledger grows, and the server pushes each of them already, so nothing is polled. What an agent uses while the main chat is still shows at the next of them. A chat that a Pi in a terminal has open pushes nothing to the app, so its page says so and is read again with the button.
- **Esc closes it**, as it closes the settings, and a run goes on: it is stopped from the chat, where it can be seen.
- **A ledger with nothing in the range** says "No usage in this period", and one with lines that cannot be read says how many, in pi-optchat's words.
- **What is left out.** "This session"; one agent's cost by itself; prices of your own; and any range but pi-optchat's.
